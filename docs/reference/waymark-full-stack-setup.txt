1) What you’re building (ELI5)
Waymark is a dark, mobile-first training system for one athlete. It is not a generic fitness app and it is not a spreadsheet clone. You are building an iPhone app that lets you see your AM / PM plan, start sessions, use timers, log training, review history, and later connect running data.
Think of Waymark as a machine with layers:
iPhone app shell (Capacitor)
↓
Web app screens (React + Vite + Tailwind)
↓
API routes (Hono)
↓
Cloudflare Worker runtime
↓
Database access (Drizzle)
↓
Cloudflare D1 database


ELI5: The phone app is what you touch. The Worker is the brain in the cloud. The database is the memory. Cursor is your coding assistant, but only if you feed it good docs and good prompts.

4) Node vs Bun — what I recommend and why
Recommendation: For your first full setup, use Node + npm. It is the safest, most documented path for Cloudflare Workers + Vite + Wrangler + Capacitor.
* Cloudflare’s official React + Vite docs and most examples are written around Node/npm.
* Wrangler workflows are documented and tested most consistently in the Node ecosystem.
* Bun can be fast, but you do not need more speed right now — you need fewer surprises.
If you want to read about Bun later: Bun + Vite guide
Bottom line: start stable, not clever.

11) Wrangler login + Cloudflare Worker basics
Wrangler is Cloudflare’s command-line tool. It creates databases, deploys Workers, and manages parts of your backend.
TERMINAL
npm install -g wrangler
wrangler --version
wrangler login


When wrangler login opens your browser, approve access.
Open the file wrangler.jsonc. It is the config file for your Worker.
wrangler.jsonc (starter shape)
{
  "name": "waymark",
  "main": "src/index.ts",
  "compatibility_date": "2024-12-01"
}


ELI5: This file tells Cloudflare what your backend is called, where it starts, and what runtime compatibility date to use.
12) Create D1 and wire the binding
Now create the database.
TERMINAL
wrangler d1 create waymark-db


Wrangler will print a database_id. Copy it.
Add the D1 binding to wrangler.jsonc:
wrangler.jsonc
{
  "name": "waymark",
  "main": "src/index.ts",
  "compatibility_date": "2024-12-01",
  "d1_databases": [
    {
      "binding": "DB",
      "database_name": "waymark-db",
      "database_id": "<PASTE_DATABASE_ID_HERE>"
    }
  ]
}


Check that the database exists:
TERMINAL
wrangler d1 list


ELI5: The binding name DB means your backend code can access the database as env.DB.
13) Install Drizzle and generate your first migration
Drizzle helps you manage your database schema in TypeScript.
TERMINAL
npm install drizzle-orm
npm install -D drizzle-kit


Create src/db/schema.ts:
src/db/schema.ts
import { sqliteTable, text, integer } from "drizzle-orm/sqlite-core";


export const sessions = sqliteTable("sessions", {
  id: text("id").primaryKey(),
  type: text("type"),
  createdAt: integer("created_at"),
});


Create drizzle.config.ts:
drizzle.config.ts
import { defineConfig } from "drizzle-kit";


export default defineConfig({
  schema: "./src/db/schema.ts",
  out: "./drizzle",
  dialect: "sqlite",
});


Generate the migration:
TERMINAL
npx drizzle-kit generate


Apply the generated SQL to your local D1 database:
TERMINAL
wrangler d1 execute waymark-db --local --file=./drizzle/0000_*.sql


Then apply it to the remote database when you are ready:
TERMINAL
wrangler d1 execute waymark-db --remote --file=./drizzle/0000_*.sql


Important: Use --local for local development. Use --remote only when you really want to change the cloud database.
Verify the table exists:
TERMINAL
wrangler d1 execute waymark-db --local --command "SELECT name FROM sqlite_master WHERE type='table';"

15) Connect Hono + Drizzle + D1
Now wire the backend to the database.
Create src/db/client.ts:
src/db/client.ts
import { drizzle } from "drizzle-orm/d1";


export function createDB(env: { DB: D1Database }) {
  return drizzle(env.DB);
}


Update the server file:
src/server/app.ts
import { Hono } from "hono";
import { createDB } from "../db/client";
import { sessions } from "../db/schema";


type Bindings = {
  DB: D1Database;
};


const app = new Hono<{ Bindings: Bindings }>();


app.get("/api/health", (c) => {
  return c.json({ status: "Waymark API running" });
});


app.get("/api/sessions", async (c) => {
  const db = createDB(c.env);
  const rows = await db.select().from(sessions);
  return c.json(rows);
});


export default app;


Insert one test row into the local database:
TERMINAL
wrangler d1 execute waymark-db --local --command "INSERT INTO sessions (id, type, created_at) VALUES ('test-session', 'strength', 1700000000);"


Test the read route:
BROWSER
http://localhost:5173/api/sessions


You should see your test row returned as JSON.
ELI5: At this point the stack is real: browser → API → Worker → database.

20) Testing, debugging, and common mistakes
Every feature should be tested in three places:
* Local browser (npm run dev)
* Local iPhone build (npm run build → npx cap sync → Xcode Run)
* Production backend when relevant (wrangler deploy → test API URL)
Most common mistakes:
* Forgetting to rebuild and sync before testing on phone.
* Forgetting to apply database migrations locally.
* Letting Cursor edit multiple systems at once.
* Using real secrets in committed files.
* Testing only in the browser and never on device.

22) Troubleshooting and glossary
Quick troubleshooting
`npm run dev` fails — Read the exact error. Often it is a missing package or a syntax error in a file you just edited.
Phone app did not update — Run npm run build, then npx cap sync, then Run again in Xcode.
D1 query fails — Check wrangler.jsonc binding, confirm database exists with wrangler d1 list, and verify you applied migrations.
API route returns 404 — Check the route path in Hono and the browser URL exactly.
Cursor keeps freelancing — Use smaller prompts and explicitly say do not modify unrelated files.

24) Timer Engine Architecture
Timers are a critical system in Waymark because training sessions depend on them.


Supported timer types:

25) Workout and Session Engine

Sessions should record:
planned sets

15) Connect Hono + Drizzle + D1
Now wire the backend to the database.

src/server/app.ts
import { Hono } from "hono";
import { createDB } from "../db/client";
import { sessions } from "../db/schema";


type Bindings = {
  DB: D1Database;
};


const app = new Hono<{ Bindings: Bindings }>();


app.get("/api/health", (c) => {
  return c.json({ status: "Waymark API running" });
});


app.get("/api/sessions", async (c) => {
  const db = createDB(c.env);
  const rows = await db.select().from(sessions);
  return c.json(rows);
});

import { Hono } from "hono";
import { createDB } from "../db/client";
import { sessions } from "../db/schema";


type Bindings = {
  DB: D1Database;
};


const app = new Hono<{ Bindings: Bindings }>();


app.get("/api/health", (c) => {
  return c.json({ status: "Waymark API running" });
});


app.get("/api/sessions", async (c) => {
  const db = createDB(c.env);
  const rows = await db.select().from(sessions);
  return c.json(rows);
});

41) Full Database Schema Example
Below is a more complete schema example for Waymark. This demonstrates how sessions,
wellness logs, and runs could be structured.


src/db/schema.ts


import { sqliteTable, text, integer } from "drizzle-orm/sqlite-core";


export const sessions = sqliteTable("sessions", {
  id: text("id").primaryKey(),
  type: text("type"),
  createdAt: integer("created_at"),
  notes: text("notes")
});


export const runs = sqliteTable("runs", {
  id: text("id").primaryKey(),
  distance: integer("distance"),
  duration: integer("duration"),
  createdAt: integer("created_at")
});


ELI5:
A schema is the blueprint of your database tables.
It tells the database what columns exist and what type of data goes in them.
